# BazarFX — апскейлер + генератор кадров для Android

> «DLSS для Android» своими руками: снижаем разрешение рендера и число кадров,
> а потом восстанавливаем картинку и дорисовываем промежуточные кадры на GPU.

Живая демонстрация: **`/fx`** (страница `app/fx/page.tsx`, движок — `lib/fx/`).

Как начать пользоваться прямо сейчас:

1. Открой `/fx` на телефоне в Chrome.
2. Нажми «Установить на телефон» — страница ставится как приложение (PWA) и
   запускается полноэкранно, как игра.
3. Вкладка **«Своё видео»** — загрузи запись геймплея (MP4/WebM), и BazarFX
   прогонит её через весь пайплайн. Ползунком сравнения видно разницу.
4. Вкладка **«Захват экрана»** (десктоп) — можно наложить BazarFX на живой экран.
5. Для своей игры в Unity — `integrations/unity/` (шейдер + компонент + инструкция).

## 1. Честно о терминах

DLSS 5 — это нейросеть, которая работает на тензорных ядрах NVIDIA и подключается
внутри движка игры. На Android такого нет и в обозримом будущем не будет. Но 80%
эффекта дают не нейросети, а классические алгоритмы:

| Что делает DLSS | Чем заменено в BazarFX |
| --- | --- |
| Рендер в низком разрешении | то же самое, `renderScale` 25–100% |
| Motion vectors из движка | G-buffer MRT: шейдер сцены пишет векторы движения |
| Temporal accumulation (TAA) | репроекция истории + variance clipping |
| Spatial upscale | Catmull-Rom реконструкция с edge-guard |
| Sharpening | RCAS-подобный контрастно-зависимый шарп |
| Frame Generation | интерполяция между кадрами по motion vectors |

То есть по классу это **FSR / XeSS-подобный пайплайн**, а не DLSS. Зато он
работает на любом Adreno/Mali с OpenGL ES 3.0 и не требует нейросетевых ядер.

## 2. Пайплайн

```
 ┌─────────────────────────────────────────────────────────────┐
 │ 1. СЦЕНА (низкое разрешение, например 480×270)              │
 │    • ray-march / обычный рендер игры                        │
 │    • jitter камеры на долю пикселя (Halton 2,3)              │
 │    • MRT: COLOR_ATTACHMENT0 = цвет, ATTACHMENT1 = velocity   │
 └───────────────┬─────────────────────────────────────────────┘
                 ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ 2. ПРОСТРАНСТВЕННЫЙ АПСКЕЙЛ (полное разрешение)             │
 │    • Catmull-Rom 4×4 (резкие края без мыла билинейки)        │
 │    • clamp к локальному min/max — без ореолов                │
 └───────────────┬─────────────────────────────────────────────┘
                 ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ 3. TEMPORAL (TAA)                                           │
 │    • history репроецируется по motion vectors                │
 │    • variance clipping (mean ± 1.6σ) убивает ghosting        │
 │    • jitter + накопление = сглаживание краёв (антиалиасинг)  │
 └───────────────┬─────────────────────────────────────────────┘
                 ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ 4. АДАПТИВНЫЙ ШАРПЕНИНГ                                     │
 │    • boost обратно пропорционален локальному контрасту        │
 └───────────────┬─────────────────────────────────────────────┘
                 ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ 5. ПРЕЗЕНТАЦИЯ / ГЕНЕРАЦИЯ КАДРОВ                            │
 │    • нет нового кадра → синтез между prev и cur по velocity  │
 │    • 24 fps игры → 60 fps на экране                          │
 └─────────────────────────────────────────────────────────────┘
```

### Почему motion vectors, а не оптический поток

Оптический поток (как в телевизорах) считается по уже готовой картинке: он
ошибается на перекрытиях и стоит дорого. Движок же знает смещение каждого
пикселя бесплатно — в демо это аналитическая формула `(uv − 0.5) · move / depth`
для движения камеры вперёд.

### Почему variance clipping

История репроецируется с ошибкой: перекрытия, края экрана, смена сцены. Если
просто смешивать, появляются «шлейфы». Мы ограничиваем историю статистикой
соседних 3×3 пикселей текущего кадра — шлейфы физически не могут выжить.

## 3. Код

```
lib/fx/shaders.ts        — GLSL ES 3.00: сцена, апскейл, temporal, шарп, вывод,
                           видео-источник, блочный оптический поток
lib/fx/engine.ts         — BazarFX: контекст, FBO, ping-pong, цикл, метрики,
                           режим источника «видео» + rVFC-синхронизация
components/fx/FxDemo.tsx — демо-страница /fx (сцена / видео / захват экрана, PWA)
integrations/unity/      — шейдер + MonoBehaviour + ScriptableRendererFeature
app/manifest.ts          — PWA-манифест (start_url /fx, fullscreen, landscape)
```

Движок не зависит от React — это чистый WebGL2-класс:

```ts
import { BazarFX } from '@/lib/fx/engine';

const fx = new BazarFX(canvas, {
  renderScale: 0.5,   // рендерим в 50% пикселей
  temporal: true,     // TAA
  upscale: true,      // Catmull-Rom
  sharpen: true,
  frameGen: true,     // 30 fps игры → 60 fps вывода
  sceneFpsCap: 30,
});

fx.resize(width, height, devicePixelRatio);
fx.onStats = (s) => console.log(s.sceneFps, s.presentFps, s.gpuMs);
fx.start();
```

`renderScale` — главный рычаг: 0.5 по каждой оси = **25% пикселей** (в 4 раза
дешевле), 0.35 ≈ 12%. Дальше качество вытягивают temporal и шарп.

## 4. Android: почему это переносится почти без изменений

Шейдеры написаны на **GLSL ES 3.00** (`#version 300 es`) — это ровно тот
диалект, который компилирует OpenGL ES 3.0 на телефонах. Отличия при переносе:

| WebGL2 | Android (GLES 3.0) |
| --- | --- |
| `#version 300 es` | без изменений |
| `layout(location=N) out` | без изменений |
| `texture()` | без изменений |
| `gl_VertexID` (fullscreen triangle) | без изменений, либо VBO с 3 вершинами |
| MRT + `glDrawBuffers` | без изменений |
| `EXT_disjoint_timer_query_webgl2` | `GL_EXT_disjoint_timer_query` |

Важные нюансы для мобилок:

1. **RGBA8 хватает**: HDR/tone-mapping делается в самом рендере сцены, буферы
   держим в 8 бит — экономия bandwidth, которая на телефоне дороже шейдеров.
2. **`mediump` для velocity**: векторы можно писать в `mediump` — точности хватает.
3. **Размер истории**: два full-res буфера + два low-res — на 1080p это ~16 МБ.
   Для бюджетных устройств можно держать `renderScale` 0.4 и историю в 720p.
4. **Тайлы**: на Mali/Adreno промежуточные проходы лучше не раздувать по числу
   смен framebuffer'ов — при желании стадии 2+3+4 схлопываются в один шейдер.

## 4.5. Источник кадров: движок или видео

Движок умеет два режима, и это ключ к тому, что технологию можно применить
**к любой игре, а не только к своей**:

| Режим | Motion vectors | Что даёт |
| --- | --- | --- |
| `source: 'game'` | пишет сам рендер (MRT) | максимальное качество, нулевая цена за векторы |
| `source: 'video'` | блочный оптический поток (block matching) | работает на любом видео/стриме, векторы считаются «снаружи» |

Блочный поток в WebGL-версии: сетка `lowRes / step`, поиск ±`search` шагов,
окно сопоставления `taps`×`taps`, SAD + параболическое субпиксельное
уточнение, затем апскейл и сглаживание поля. Стоимость настраивается:

| Пресет потока | step | search | окно | Охват | Когда |
| --- | --- | --- | --- | --- | --- |
| Быстрый | 4 | ±3 | 3×3 | ±12 px | бюджетные телефоны |
| Баланс | 3 | ±4 | 3×3 | ±12 px | по умолчанию |
| Точный | 2 | ±5 | 5×5 | ±10 px | медленный контент, десктоп |

Векторы блочного поиска почти всегда грубее, чем G-buffer движка, поэтому при
`renderScale` < 0.4 поток можно выключить — останется апскейл + шарп
(качество уровня FSR 1.0).

Переключение — одна строка:

```ts
fx.setVideo(videoElement);   // видео как источник
fx.setVideo(null);           // назад к процедурной сцене
```

Синхронизация — через `video.requestVideoFrameCallback`, поэтому пайплайн
работает ровно по кадрам видео, а генерация кадров вставляет промежуточные
между ними (24/30 fps ролик → 60 fps на экране).

## 5. Как встроить в настоящую игру

Есть три реальных пути, от простого к сложному:

### A. Внутри движка (самый качественный)

* **Unity (URP/HDRP)**: готовые файлы в `integrations/unity/` —
  `BazarFXUpscale.shader` + `BazarFXController.cs` + пример
  `ScriptableRendererFeature`. Motion vectors берутся из
  `_CameraMotionVectorsTexture` URP.
* **Unreal**: пост-процесс материал в `PostProcessVolume` + `r.ScreenPercentage`.
* **Свой движок**: подключаем `lib/fx/shaders.ts` напрямую.

### B. Внешний рендер-хук (для готовых APK)

Через Vulkan layer или GLES-перехват (как ReShade) можно заставить игру рисовать
в FBO меньшего размера и вставить наш пост-проход. Ограничение: без доступа к
motion vectors движка придётся считать поток по экрану (block-matching на GPU).
Это дороже и хуже качеством, но всё ещё даёт прирост.

### C. PWA / стриминг

Тот же код крутится в браузере поверх `<canvas>` — актуально для облачных
сервисов и веб-игр (и именно это работает на странице `/fx`).

## 6. Что реально даёт прирост

Экономия считается честно:

```
пиксели сцены   = renderScale²      → 0.5² = 25%
стоимость кадра = пиксели + оверхед  → оверхед апскейла ≈ 0.3–0.6 мс на десктопе
FPS             = 1 / (scene + fx)
```

При `sceneFpsCap = 24` и включённой генерации кадров вывод идёт на 60+ fps, но
**задержка ввода** остаётся как у 24 fps (это принципиальное свойство любой
frame generation, включая DLSS 5 / FSR FG). Для шутеров это чувствуется —
там лучше использовать только апскейл, для стратегий/гонок/кино-игр генерация
кадров даёт плавность почти бесплатно.

### Замер на своём устройстве

В демо есть кнопка **«Замерить на этом устройстве»**: она 20 раз рисует кадр
«как обычно» (сцена в полном разрешении) и 20 раз — кадр с BazarFX (сцена в
lowRes + весь пайплайн), каждый раз с `gl.finish()`, и показывает миллисекунды
на кадр и потолок FPS для обоих вариантов.

Это единственный честный способ узнать цифры для конкретного телефона: у
разных Adreno/Mali баланс между стоимостью пикселей и стоимостью шейдерных
проходов отличается в разы. Если выигрыш < 1× — поднимите `renderScale` или
выключите temporal/поток.

### Замеры (референсная CPU-реализация того же пайплайна)

Сцена из демо, рендер 480×270 → вывод 960×540, 24 кадра подряд, камера в движении.

| Вариант | Высокочастотная энергия (резкость) | PSNR к 3× supersampling |
| --- | --- | --- |
| Билинейный апскейл | 0.0101 | 24.47 дБ |
| Catmull-Rom + шарп | **0.0120 (+19%)** | 24.19 дБ |
| Catmull-Rom + TAA (α=0.15) | 0.0120 | **24.90 дБ (+0.43)** |
| Catmull-Rom + TAA + шарп | 0.0120 | 24.85 дБ |

Вывод: пространственная часть даёт резкость (+19% деталей), временная —
стабильность и антиалиасинг (+0.43 дБ к «идеальному» суперсэмплингу). Шарп
слегка снижает PSNR, потому что осознанно подчёркивает детали — это ожидаемо,
метрика PSNR не любит резкость.

## 7. Установка как приложение (PWA)

`/fx` ставится на домашний экран Android-телефона:

* `app/manifest.ts` — `start_url: /fx`, `display: fullscreen`,
  `orientation: landscape`, иконки 192/512 (в т.ч. maskable);
* `metadata.appleWebApp` + `viewportFit: cover` — корректно на iOS и при вырезе;
* в шапке страницы кнопка «Установить на телефон» (через
  `beforeinstallprompt`), на iOS — «Поделиться → На экран Домой».

В standalone-режиме браузер не показывает адресную строку, поэтому демо
работает как обычное приложение и в полноэкранном режиме (кнопка
«Полный экран» на самой странице).
